# Лабораторна робота №3 : Моніторинг ML API та детекція проблем

## Опис проєкту
Розширення ML API з Лабораторної роботи №2: додано повноцінний шар моніторингу на базі Prometheus, детектор зсуву вхідних даних (data drift) на основі KS-тесту Колмогорова-Смирнова та структуроване JSON-логування усіх ключових подій сервісу.

## Стек технологій

- **Python 3.13**, FastAPI, Pydantic v2
- **prometheus-client** — інструментування метрик
- **scipy** — KS-тест для drift detection
- **python-json-logger** — структуроване JSON-логування
- **pandas, numpy** — обробка даних для звіту
- **scikit-learn, joblib** — модель та серіалізація
- **Docker, docker-compose** — контейнеризація та оркестрація
- **Prometheus** — збір та зберігання метрик

## Висновки

У ході виконання лабораторної роботи було побудовано повноцінний
спостережуваний ML-сервіс. Реалізовано інструментування коду метриками
Prometheus семи типів, що дозволяє відстежувати latency, throughput та
розподіл прогнозів у реальному часі. Детектор drift на основі KS-тесту
дозволяє автоматично виявляти зсув вхідних даних без необхідності
очікувати деградації метрик якості моделі. Структуроване JSON-логування
забезпечує повний аудит усіх рішень моделі.

## Контрольні питання:


### 1. Поясніть різницю між моніторингом класичного веб-сервісу та моніторингом ML-сервісу. Які метрики потрібно додатково збирати у ML-системі і чому стандартних метрик типу latency / error rate недостатньо для виявлення проблем із моделлю?

Класичний веб-сервіс описується лише кодом, тому стандартні метрики
(latency, error rate, throughput) повністю відображають його стан.
ML-сервіс має три джерела складності: код, дані та модель. Модель може
тихо деградувати без жодних помилок 500 — сервіс відповідає 200 OK,
але якість прогнозів падає через зміну вхідних даних.

Тому в ML-системі додатково збирають:
- **Розподіли вхідних ознак** — щоб виявити data drift (зсув даних
  відносно тренувальних)
- **Впевненість моделі (predict_proba)** — падіння середньої
  впевненості свідчить, що модель бачить незвичні дані
- **Розподіл прогнозів за класами** — якщо один клас раптом займає
  90% прогнозів замість звичних 33%, це сигнал проблеми
- **Метрики якості моделі** (accuracy, F1) — там, де доступні реальні
  мітки з затримкою

Стандартних метрик недостатньо тому, що вони вимірюють лише технічну
справність сервісу, але не якість рішень, які він приймає.

### 2. Поясніть pull-модель Prometheus. Що відбувається, коли ML API повертає 500 на запит до /metrics або взагалі стає недоступний? Чи помітить це Prometheus, і у який спосіб?

Prometheus працює за pull-моделлю: він сам ініціює HTTP-запит GET /metrics
до кожного зареєстрованого target-у з інтервалом scrape_interval (у нас 10s).
Це протилежність push-моделі, де клієнт сам надсилає дані.

Якщо ML API повертає 500 на запит до /metrics або стає повністю
недоступним, Prometheus:
- Помічає ціль як **DOWN** у розділі /targets
- Записує метрику `up{job="ml-api"} 0` замість звичного `1`
- Продовжує спробувати кожні scrape_interval секунд
- Не втрачає раніше зібрані дані — вони залишаються у TSDB

Це одна з переваг pull-моделі: стан кожної цілі завжди видно
в інтерфейсі Prometheus, і недоступність сервісу автоматично стає
метрикою, на яку можна налаштувати алерт.


### 3. У чому принципова різниця між метриками типу Counter, Gauge та Histogram?

**Counter** — лічильник, який може лише зростати (або обнулятись при
перезапуску). Використовується для підрахунку подій: кількість запитів,
кількість прогнозів, кількість помилок. На графіках показують не саме
значення, а швидкість зростання через `rate()`. Приклад у нашому
проєкті: `ml_predictions_total`.

**Gauge** — показник, який може як зростати, так і спадати. Підходить
для миттєвих вимірювань поточного стану: кількість активних з'єднань,
споживання пам'яті, температура. Приклад у нашому проєкті:
`ml_model_loaded` — приймає значення 1 (модель завантажена) або 0 (ні).

**Histogram** — збирає розподіл значень за заздалегідь визначеними
"кошиками" (buckets). Дозволяє обчислювати перцентилі (p50, p95, p99).
Використовується для latency та розподілу впевненості моделі. Зберігає
три ряди: `_bucket`, `_sum`, `_count`. Приклади у проєкті:
`ml_prediction_latency_seconds` та `ml_prediction_confidence`.

### 4. Поясніть, що таке data drift і чому він є серйозною загрозою для ML-моделей у продакшені, навіть коли сервіс не повертає жодної помилки. Назвіть і поясніть три можливі причини виникнення drift на конкретному прикладі (можна на гіпотетичному ML-сервісі – наприклад, оцінки кредитного ризику).

Data drift — це зміна статистичного розподілу вхідних даних у
продакшені порівняно з тренувальними даними. Небезпека в тому, що
модель продовжує повертати 200 OK і не генерує жодних технічних помилок,
але якість прогнозів непомітно деградує. Знижується accuracy,
зростає кількість хибних спрацювань — і це відображається лише на
бізнес-метриках, а не на технічних.

**Три причини drift на прикладі ML-сервісу оцінки кредитного ризику:**

1. **Зміна середовища.** Модель навчалась на даних 2019 року, коли
   середня зарплата у вибірці становила 15 000 грн. У 2024 році через
   інфляцію середня зарплата — 35 000 грн. Модель систематично занижує
   ризик, бо сприймає сучасні зарплати як ознаку заможності, хоча
   реальна купівельна спроможність не змінилась.

2. **Зміна джерела даних.** Банк підключив новий канал — мобільний
   додаток для молоді. Нова аудиторія має інший профіль: молодший вік,
   менший кредитний стаж, інша структура витрат. Модель, навчена на
   клієнтах відділень, не бачила таких патернів і масово видає
   некоректні оцінки.

3. **Помилка в пайплайні обробки даних.** Після оновлення ETL-процесу
   колонки з доходом та боргом переплутались місцями. Модель отримує
   технічно валідні числа (валідація Pydantic не спрацьовує), але
   семантично зовсім інші — і її прогнози стають випадковими.

### 5. Поясніть, як працює KS-тест Колмогорова-Смирнова та що означає p-value у його результаті

KS-тест (Kolmogorov-Smirnov) — непараметричний статистичний тест, який
перевіряє нульову гіпотезу H0: "дві вибірки походять з одного
розподілу". Непараметричний означає, що не потрібно припускати
нормальність — тест працює з будь-якими неперервними числовими даними.

**Як працює:** тест будує емпіричні кумулятивні функції розподілу (CDF)
для обох вибірок і знаходить максимальну відстань D між ними. Якщо
розподіли однакові — їх CDF збігаються і D ≈ 0. Чим сильніше
відрізняються вибірки — тим більше D.

**Що означає p-value:** на основі статистики D та розмірів вибірок
тест обчислює p-value — імовірність побачити таке ж або більше
розходження між вибірками, якщо насправді вони походять з одного
розподілу (тобто за умови, що H0 істинна).

**Інтерпретація:**
- `p-value < α (0.05)` → розходження занадто велике для випадковості →
  відкидаємо H0 → **drift виявлено**
- `p-value ≥ α (0.05)` → розходження пояснюється випадковістю →
  немає підстав відкидати H0 → **drift не виявлено**

У нашому звіті: для `petal_length` KS statistic = 0.395, p-value ≈ 0.0
— drift очевидний, бо ми навмисно зсунули значення на +1.5. Для інших
ознак p-value > 0.98 — зміни статистично незначущі.
