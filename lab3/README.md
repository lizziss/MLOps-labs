# Лабораторна робота №2: CI/CD та ML API

## Опис проєкту
Цей проєкт реалізує наскрізний MLOps-конвеєр для класифікації  Iris. Сервіс включає автоматизоване тренування моделі логістичної регресії, надання доступу до неї через REST API на базі FastAPI та автоматизацію перевірок за допомогою GitHub Actions.

## Стек технологій
* **Мова програмування:** Python 3.11 
* **ML бібліотеки:** Scikit-learn, Joblib 
* **API фреймворк:** FastAPI, Uvicorn
* **Валідація даних:** Pydantic 
* **Тестування:** Pytest, HTTPX 
* **Контейнеризація:** Docker 
* **CI/CD:** GitHub Actions 
* **Деплой:** Render 

## Як запустити локально
1. **Клонуйте репозиторій та перейдіть у каталог:**
   ```bash
   git clone https://github.com/lizziss/MLOps-labs.git
   cd MLOps-labs/lab2
   ```
2. **Налаштуйте віртуальне оточення:**
   ```bash
     python -m venv .venv
     source .venv/bin/activate  # Для Linux/macOS
     # або .venv\Scripts\activate для Windows 
   ```
3. **Встановіть залежності та навчіть модель:**
   ```bash
    pip install -r requirements.txt
    python -m ml.train
   ```
4. **Запустіть API:**
   ```bash
   uvicorn app.main:app --reload
   ```

## Запуск через Docker
Локальний запуск тестів для перевірки коду та моделі:
  ```bash
  docker build -t ml-api:lab2 .
  docker run --rm -p 8000:8000 ml-api:lab2
  ```


## Як запустити тести
```bash
pytest -q
```

## Як працює API 
Після запуску доступна інтерактивна документація Swagger UI за адресою /docs. 
* GET /health: Перевірка статусу сервісу та підтвердження завантаження моделі.
* POST /predict: Приймає параметри IrisFeatures та повертає PredictionResponse з іменем класу та ймовірністю.

## Структура репозиторію 
Згідно з принципом єдиної відповідальності, код API, тренування та тести розділені на окремі пакети:

* `app/` — FastAPI застосунок та Pydantic-схеми.

## Контрольні питання:
### 1. У чому полягає принципова різниця між Continuous Integration і Continuous Deployment? 
Принципова різниця полягає в обсязі автоматизації процесу релізу. Continuous Integration (CI) фокусується на регулярній інтеграції змін у спільну гілку, де автоматично запускаються збірка та тести для перевірки цілісності коду. Continuous Deployment (CD) йде далі й автоматично розгортає кожну нову версію застосунку, яка пройшла CI-перевірки, безпосередньо у робоче середовище без участі людини. Таким чином, CI гарантує якість коду, а CD забезпечує його миттєву доставку користувачу.
### 2. Поясніть взаємозв'язок понять Workflow, Job та Step у GitHub Actions.
Ці поняття утворюють ієрархічну структуру автоматизації: Workflow — це найвищий рівень, загальний автоматизований процес, що описується у YAML-файлі та запускається певною подією, як-от push. Всередині workflow містяться одна або кілька Jobs (задач), які виконуються на окремих віртуальних машинах (runners) паралельно або послідовно. Кожна задача складається з окремих Steps (кроків) — конкретних команд або дій, які виконуються послідовно на одному runner-і та мають спільну файлову систему.
### 3. Яку проблему розв'язує винесення завантаження моделі у хук @app.on_event("startup") у файлі app/main.py? Як змінилися б продуктивність і час відповіді, якщо б joblib.load(...) виконувався всередині функції predict?
Винесення завантаження моделі у хук @app.on_event("startup") дозволяє завантажити важкі ваги моделі в оперативну пам'ять лише один раз під час запуску сервера. Якби joblib.load() виконувався всередині функції predict, сервер витрачав би додаткові десятки мілісекунд на дискові операції при кожному запиті користувача. Це значно знизило б продуктивність і збільшило час відповіді API, роблячи його неефективним під навантаженням.
### 4. Поясніть, чому у Dockerfile спочатку виконується COPY requirements.txt і встановлення залежностей, а лише потім – COPY коду. Як це впливає на час повторної збірки образу при зміні лише одного рядка у app/main.py?
У Dockerfile спочатку виконується копіювання requirements.txt та встановлення залежностей, а лише потім копіюється код, щоб максимально використати механізм кешування шарів. Якщо розробник змінює лише один рядок у app/main.py, Docker бачить, що файл залежностей не змінився, і використовує вже готовий (закешований) шар із встановленими бібліотеками. Це критично прискорює повторну збірку образу, оскільки системі не потрібно щоразу заново завантажувати та встановлювати всі пакети з мережі.
### 5. Як FastAPI обробляє ситуацію, коли клієнт надсилає у /predict тіло з рядком замість числа (наприклад, "sepal_length": "abc")? Яку роль у цьому відіграє Pydantic-схема IrisFeatures та який саме HTTP-код буде повернуто
Коли клієнт надсилає некоректні дані (наприклад, рядок замість числа), FastAPI автоматично перехоплює цю помилку завдяки Pydantic-схемам. Схема IrisFeatures описує "контракт" API, перевіряючи відповідність типів та меж значень вхідних параметрів. У разі невідповідності (наприклад, "abc" замість float), сервіс негайно повертає HTTP-код 422 Unprocessable Entity з деталізацією помилки, навіть не починаючи виконання логіки передбачення.
